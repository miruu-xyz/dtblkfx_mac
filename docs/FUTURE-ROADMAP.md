# Future roadmap

Things deliberately deferred out of a phase rather than dropped. Nothing here is
scheduled; it is a place to park work that was scoped, understood, and judged
not worth doing yet, so the reasoning does not have to be rediscovered.

---

## Bespoke text entry for `FX_VAL`

**Deferred from Phase 5.** That phase wires `valueFromString` for the globals,
`FrqA`/`FrqB`, `FX_AMP` and `FX_TYPE`, all of which already have an inverse
function in the engine. `FX_VAL` accepts a bare `0..1` number and nothing else.

**What is missing.** `FX_VAL` means something different in each of the 31
effects, and `FxRun1_0::dispVal` formats it about a dozen different ways. Typing
those strings back in would need one parser per format:

| Shape | Example | Effects |
| --- | --- | --- |
| Signed percentage | `-75%` | Contrast |
| Plain percentage | `50%` | Smear, Clip |
| Percentage + harmonic mode | `40% odd` | HarmFilt, AutoHarm, the five `*Mask` effects, HarmMatchLR/RL |
| Threshold direction + percentage | `above 25%` | Threshold, ThreshMask |
| Signed note offset | `+12.00 notes` | Shift, Resample, HarmShift |
| Absolute note, or a right-channel offset | `c-4:+00`, `right+12.00notes` | HarmRepitch |
| Frequency | `-1.50kHz` | ConstShift |
| Percentage + time direction | `-800% time fwd` | Resize |
| Waveform mode + percentage | `copy0/100%` | Triangles, Squares, Saws, Pointy, Sweep |
| Segment count, or percentage + mode | `229 segs`, `100% multiply` | Vocode |
| Channel cross percentage | `100%L on R` | CrossMix |
| Amount + mode index | `100 mode 1` | WarpMix |

`docs/PARAMETERS.md` has the full sweep and the value presets for every one of
them, generated by `dtblkfx_render --params`.

**Why it was deferred.** Thirty-one parsers is real work with a large surface for
subtle mistakes — several of these formats are non-monotonic packed values where
a plausible-looking parse lands on the wrong mode — and the value-preset menus
already give named entry points to the same values. The payoff is typing into a
host's parameter field, which is not how anyone reaches for these controls.

**What would make it worth doing.** A user actually wanting to type exact values,
or the Phase 6 GUI growing an editable text field on the FX value control. If it
is picked up, do it per effect as a virtual `parseVal` alongside `dispVal` so
each format lives next to the code that prints it, and drive the round-trip test
off `docs/PARAMETERS.md` — every row in that file is a `dispVal` output that
`parseVal` should map back to the same value.

## Sample-rate-scaled engine buffers

**Deferred from the Phase 5 sample-rate audit.** The engine has no fixed
internal rate and does not resample: `prepareToPlay` pushes the host rate into
the engine and flushes (`src/DtBlkFxProcessor.cpp`), and every frequency- and
time-derived quantity is computed from it — band edges (`DtBlkFx.hpp`,
`getFFTBin`), bin↔Hz (`FxRun1_0.cpp`), the constant frequency shift, millisecond
delay, and `_samps_per_beat`, which is recomputed on every tempo poll.
`GlobalCtrl` explicitly notices a rate change and rebuilds its display state.
Rendering all 71 harness cases at 96 kHz and 192 kHz produced no NaNs and peaks
in the same range as the 44.1 kHz baseline.

**What is missing.** The buffers are sized in samples from `44100` literals in
the `DtBlkFx` constructor (`src/core/DtBlkFx.cpp`), allocated once before any
sample rate is known and never resized:

```
_x0_sz       = X0_INDEX_ROUNDING_MASK & (8 * 44100);   // input buffer
_x3_sz       = 5 * 44100;                              // output buffer
_max_delay_n = _x3_sz - MAX_FFT_SZ - 2048;             // 137812 samples
```

So their capacity in *time* shrinks as the rate rises:

| Sample rate | Max delay | Input buffer | Longest FFT window |
| --- | --- | --- | --- |
| 44100 | 3.12 s | 8.00 s | 1.83 s |
| 48000 | 2.87 s | 7.35 s | 1.68 s |
| 96000 | 1.44 s | 3.67 s | 0.84 s |
| 192000 | 0.72 s | 1.84 s | 0.42 s |

`getDelaySamps` clamps to `_max_delay_n`, so the delay control — which can ask
for up to 6000 ms or ~8 beats — already saturates above 3.12 s at 44.1 kHz, and
the saturation point halves at 96 kHz. A beat-synced delay that reaches 6.25
beats at 120 bpm reaches 2.87 at 96 kHz.

Two related effects are **not** buffer bugs and should not be "fixed" alongside
it. `FFT_LEN` selects a length in samples, so the same setting is half the time
window and double the frequency resolution at 96 kHz — a preset legitimately
sounds different at a different rate, and that is original DtBlkFx behaviour.
`ConstShiftProcess::paramToHz` spans ±22050 Hz regardless of Nyquist
(`FxRun1_0.cpp`), which is harmless above 44.1 kHz and only overshoots at rates
below it.

**Why it was deferred.** Scaling the buffers means reallocating on every rate
change, which is exactly the kind of edit the Phase 3 landmine warns about: the
`fftwf_malloc` buffers are cleared once in the constructor precisely because
`init()`/`suspend()` are the wrong places, and a reallocation path would have to
re-establish that clear without moving it. It also moves the delay clamp point,
so audio changes by design and every baseline that involves delay has to be
re-listened to and regenerated. The payoff is longer delays at high rates, in a
plugin whose useful delay range is already well under the 44.1 kHz cap.

**What would make it worth doing.** Working at 96 kHz and hitting the delay
ceiling in practice. If it is picked up: keep the sizes in seconds, multiply by
the rate at allocation, reallocate from `prepareToPlay` only when the rate
actually changed, keep the constructor's zeroing of `x0`/`x1`/`x2` attached to
the allocation rather than to `init()`, and add a harness rate flag —
`kSampleRate` is currently `constexpr`, so the 96/192 kHz renders above needed a
temporary edit — so the fingerprints can be compared across rates.

**Not deferred, unrelated, still open.** The `DtBlkFxAudioProcessor` constructor calls
`core->setSampleRate(getSampleRate())`, and JUCE's `getSampleRate()` is `0`
until `prepareToPlay`, so that line replaces the stub's 44100 default with zero.
Anything reading the rate before the first prepare divides by it — the engine's
DELAY display returns `inf sec`. Latent only because nothing yet routes the
engine's display strings into `valueToText`; deleting the line is the whole fix.
